# Contributing to CertPing

Thanks for helping. This file covers everything from a fresh clone to a merged pull request.

## Before you start

- For anything bigger than a small fix, open an issue first so we can agree on the approach.
- Security problems go through [SECURITY.md](SECURITY.md), never a public issue.
- Never commit secrets, private keys, real certificates with keys, customer data or internal
  hostnames, including in tests and fixtures.
- Questions about the code or how to use CertPing: ask in
  [GitHub Discussions](https://github.com/certping-labs/certping/discussions). Other ways to get
  help are in [SUPPORT.md](SUPPORT.md).

## Build and check

`make` wraps each app's own tooling. CI runs the same targets, so a green `make ci` locally means
the checks that gate pull requests pass.

```sh
make help        # every target
make setup       # install dependencies from the lockfiles
make hooks       # once: use the repository's pre-commit hooks
make ci          # lint, typecheck, test and build everything
make web-ci      # or one app: web-ci, server-ci, agent-ci, notifier-ci
```

Per Java app there are also `<app>-setup`, `<app>-test` and `<app>-build`, for example
`make agent-build`.

## Run it locally

The supported development loop builds the images from your checkout and runs them with the
Compose kit. There is no message broker or cloud service to start.

```sh
make up          # once: writes deploy/compose/.env with fresh secrets; then builds and starts
grep '^BOOTSTRAP_SUPER_ADMIN_PASSWORD=' deploy/compose/.env
```

Open http://localhost and sign in as `admin` with that password (without the single quotes
around it). After a change, run `make up`
again to rebuild and restart. `make down` stops the stack and keeps the data volumes. Local
builds are tagged `dev` so they never mix with a release.

`make images` builds every image under the tag `dev`, plus the all-in-one as
`certping-allinone:dev`, which the end-to-end lab uses.

### Web app with hot reload

Start the Compose stack, then run the Next.js dev server against it. Create `apps/web/.env.local`:

```sh
NEXT_PUBLIC_API_URL=/api-proxy
CERTPING_API_TARGET=http://localhost
NEXT_PUBLIC_APP_MODE=enterprise
```

and run `make web-dev` (http://localhost:3000). `/api-proxy/*` forwards to the Compose proxy, so
the browser makes no cross-origin calls. `NEXT_PUBLIC_APP_MODE=enterprise` matches what the
images build. This setup follows `apps/web/.env.example`; CI does not exercise it.

### Java apps

The Java apps need the environment the kits provide (database, Valkey, JWT keys, pepper,
tokens), so the way to run your change is to rebuild its image with `make up`. Each
app's README lists its settings.

## Tests

| What | Command | Notes |
| --- | --- | --- |
| Web unit and component tests | `make web-test`, or `pnpm test` in `apps/web` | Jest and Testing Library |
| Java unit and integration tests | `make server-test`, `make agent-test`, `make notifier-test` | `mvn verify`. Testcontainers suites need a running Docker daemon. |
| One Java test class | `cd apps/server && mvn -Dtest=RenewalTimingTest test` | Standard Surefire selection |
| Helm charts | `make helm-lint` | Lints and renders both charts |
| Whole product | `make images && deploy/e2e-lab/run.sh` | Issue, deploy, discover, renew, alerts and email for real on one machine; about 4 GB of memory ([deploy/e2e-lab/README.md](deploy/e2e-lab/README.md)) |

Add or update tests that show the change works. Tests that exist only to make CI pass are not
accepted. Code that handles private keys, credentials or tenant boundaries needs a test for the
failure path too, for example that a key never appears in a log, an API response or an audit
record. A change to an integration that the lab cannot run (a cloud target, a commercial CA)
should say in the pull request how it was checked.

## Code style

| Area | Rule |
| --- | --- |
| Web | ESLint and Prettier. `make web-lint` runs the typecheck, ESLint and the Prettier check; `pnpm format` in `apps/web` fixes formatting. |
| Java | No formatter is enforced. Follow the style of the surrounding code; the apps use Lombok and Spring Boot conventions. |
| Database | Schema changes are new Flyway migrations in `apps/server/src/main/resources/db/migration`, never edits to existing ones. Migrations only go forward. |
| Headers | Every source file starts with `Copyright Seaionl Inc. and CertPing contributors` and `SPDX-License-Identifier: Apache-2.0` in its comment style. `make license-headers` adds them to new files; CI checks them. Contributors keep their copyright ([AUTHORS.md](AUTHORS.md)); the header names the project's authors as a group. |
| Docs | Plain, direct English, short sentences, no marketing words. Every command must be copy-pasteable, and every setting, label and path must match the code. Update the docs in the same pull request when behavior, configuration or an API changes. |

## Security scans

The same tools and versions as CI:

```sh
make scan-secrets   # gitleaks over the current branch's history
make scan-deps      # trivy over dependencies, Dockerfiles and charts
```

## Dependencies and third-party notices

After any dependency change (a `pom.xml`, `package.json` or lockfile, or a base image), run
`.github/scripts/third-party-notices.sh` (or `make notices`) and commit the files it updates under
`licenses/` and `apps/*/licenses/`. A base image change also needs the versions read from the new
image ("Base image updates" in [.github/RELEASING.md](.github/RELEASING.md)). It needs Maven with the apps' dependencies downloaded (run a
build first), JDK 25, Node.js 24 and `pnpm install` done in `apps/web`. CI runs it with `--check`
(`make notices-check`) and fails when the files are out of date.

## Branches (GitHub Flow)

- `main` is the only long-lived branch and must always build.
- Work on a short-lived branch named for its purpose: `feat/...`, `fix/...`,
  `docs/...`, `security/...`, `chore/...`.
- Open a pull request into `main`. It is squash-merged and the branch deleted.

## Pull request titles

Use [Conventional Commits](https://www.conventionalcommits.org/) for the PR
title, because it becomes the squashed commit message:

```
feat(agent): add Route 53 DNS-01 support
fix(server): stop renewal retries after revocation
docs: explain the PQC readiness report
```

Scopes in use: `web`, `server`, `agent`, `notifier`, `helm`, `ci`, `docs`. Mark
breaking changes with `!` (for example `feat(server)!: ...`) and describe the
upgrade path in the PR.

## Pull request checklist

The [pull request template](.github/pull_request_template.md) asks for these; check them before
you ask for review:

- [ ] `make ci` passes, or the `<app>-ci` target of every app you changed.
- [ ] Tests added or updated for the change.
- [ ] No secrets, private keys, customer data, real hostnames or internal endpoints anywhere.
- [ ] Private keys and credentials are never logged, returned by an API or written to audit records.
- [ ] Docs updated if behavior, configuration or an API changed.
- [ ] Third-party notices regenerated if a dependency changed.
- [ ] Breaking change marked with `!` in the title, with the upgrade path described.
- [ ] Every commit signed off (next sections).

## Review and merge

- Every pull request, including the team's own, needs one approval from the
  CertPing team (`@certping-labs/certping`, the code owners), from someone
  other than its author. Changes reach `main` only through a pull request.
- The `ci-required` and `Security` checks pass.
- All conversations resolved. A substantive push after approval needs a fresh
  review.
- AI review comments, when enabled, are advisory. They never replace the human
  approval.
- Every commit carries a DCO sign-off (next section). CI checks it (the
  `DCO sign-off` job, part of `ci-required`); a pull request with a commit that
  is not signed off is not merged until it is fixed.

## Sign-off (DCO)

Sign off each commit with `git commit -s`. It adds a
`Signed-off-by:` line certifying the
[Developer Certificate of Origin](https://developercertificate.org/): that you
wrote the change or have the right to submit it under the project's license.
Sign-off is not a transfer of copyright. If you forgot it, fix the branch with
`git rebase --signoff main` and force-push.
